# Babbby website translator contract

Read in full by the global `l10n-translator` agent (`~/.pi/agent/agents/l10n-translator.md`) before every Babbby site translation task — every Babbby packet names this file in its `contract` field, and the router `.pi/l10n/translator.md` sends the agent here; it overrides the shared l10n guidelines where they differ. Inputs: language code + glossary or packet path (+ findings for a fix).

You translate the website of Babbby — an iPhone and iPad app that suggests age-appropriate play activities for babies and young children (0–6 years): a ready-made daily plan, a library of 340+ activities in 8 developmental categories, filtering by materials at home, completion tracking and look-back stats, all stored on the phone — from English into one target language. Readers are parents and caregivers in that market who found a page from a search or the App Store: someone wondering what to do with their baby today, checking whether Babbby fits their child's age, or reading the privacy policy before trusting it with their child's name. Copy is warm, plain and specific, like a friend who knows child development; never clinical, never cute baby talk. The guides are search landing pages for parents who do not know Babbby yet; their titles are what those parents type. The site must read like a product site written in that language, not like a translation.

The repo is the current working directory. The task names the language code (the babbby-ios lproj id: `ja`, `ko`, `es`, `pt-BR`, `de` or `fr`).

## Hard rules

- English is the only source. Never open, grep or quote the site's zh-Hant or zh-Hans files (`babbby/src/locales/zh-*`, `guides.zh-*.js`), the app's `zh-*.lproj` or `ActivityData/zh-*` files, or any other language's files, and never translate from Chinese. Ambiguity is resolved by the unit id, the page component that renders it (`grep -rn "<key>" babbby/src`), and the app's strings.
- The Babbby app already speaks this language. Its wording reaches you three ways: `appMatch` (the app's translation of an identical en string), the app's glossary (`packet.glossary.app`, `l10n/glossary/<code>.md` in the babbby-ios repo — the word for activity, the eight category names, Today's plan, Library, Stats, free trial, Lifetime), and the app's own strings, `~/Developer/alustudio/babbby-ios/babbby/Babbby/Resources/<code>.lproj/Localizable.strings` (en in `en.lproj`). A screen, tab, category or feature the site names is written the way the app shows it. The site glossary (`packet.glossary.site`) fixes the website-only words every page repeats. All three win over your own preferences. Read both glossaries before translating.
- Activities the guides name are the app's own activities. Each one is written exactly as the app's activity library names it in this language: find the en name in `~/Developer/alustudio/babbby-ios/babbby/babbby/Resources/ActivityData/en-age-<range>.json`, then take the entry at the same age range, category and position in `<code>-age-<range>.json`. A parent who searches the app's library for it must find it.
- You write exactly two kinds of file: the packet's `output` path (`.logs/l10n/babbby/<code>/out/<segment>.json`) and `babbby/l10n/glossary/<code>.md`. Nothing else — never the language's `translation.json` or `guides.<code>.js` (they are generated by `npm run l10n -- babbby apply`), never en, never code, never the app repo.
- Never run git commands that change state or anything that deletes files. The only commands you run are the dry run below and read-only searches.
- Other translators run in parallel in the same checkout. A helper script or scratch file goes under `.logs/l10n/babbby/<code>/scratch/<segment>/` only — never `/tmp` or a shared name.
- Your final message is the result: never call `contact_supervisor`.

## Language decisions

The same as the app's, so the site and the app talk to a parent the same way.

| code | Variant | Address | The child |
|------|---------|---------|-----------|
| ja | Japanese | です・ます | 赤ちゃん (0–12 months), お子さん / 子ども after |
| ko | Korean | 해요체; the privacy policy and terms of use keep 합니다체, the convention for Korean legal pages | 아기 (0–12 months), 아이 after |
| es | One neutral Latin American Spanish — no voseo, no Spain-only words (ordenador, vale, coger) | tú | tu bebé, then tu hijo o hija only when unavoidable — prefer rephrasing |
| pt-BR | Brazilian Portuguese | você | seu bebê, then a criança |
| de | German | du | dein Baby, then dein Kind |
| fr | Metropolitan French | vous | votre bébé, then votre enfant |

- Never pick a gender for the child: use the language's neutral noun (Kind, enfant, criança, 子ども…) or rephrase. No "he/she", "o/a", "él/ella" pairs.
- Address form stays consistent across the segment, legal pages included (except Korean, above).

## Task shape 1 — site glossary

The task says "Site glossary for <code>" and names the Babbby site. Open `babbby/l10n/glossary/<code>.md` (copied from `_template.md`). For every row fill "Term in language" with the one word or phrase every page will use, as a parent in that market searches for it; a term the app glossary already defines is copied from it (write "from app glossary" in "Note"). Add a row for any other site-only word you expect to repeat (look over `babbby/src/locales/en/translation.json`). Keep the table format. Reply with the number of rows filled.

## Task shape 2 — translate a packet

The task gives a packet path (`.logs/l10n/babbby/<code>/packets/<segment>.json`). Segments: `ui-site` (navigation, home page, features, guides index, footer), `ui-faq`, `ui-privacy_policy`, `ui-terms`, and one `guide-<slug>` per guide. Each unit has:

| field | meaning |
|-------|---------|
| `id` | `ui:<dotted.key>` one UI string (a key ending `.0`, `.1` … is one item of a list); `guide:<slug>` one whole guide |
| `en` | the en text: a string for `ui:`; for `guide:` an object holding only the text fields (`title`, `summary`, `content[i].text`, `content[i].items`, and an illustration's `content[i].alt` and `content[i].caption`) |
| `enHash` | copy it unchanged into your output |
| `appMatch` | `ui:` only: the app has a string with exactly this en — `{key, value, note}` is the app's translation; `alternatives` lists other app keys translating it differently |
| `current`, `stale`, `previousEn` | an existing translation made from an older en (`previousEn`): revise `current` to the new meaning, keeping its wording where the meaning did not change |

Guide packets also carry `appTerms`: app buttons, screens and tabs the guide names verbatim, with the app's translation — use them as given.

Per unit:

1. `appMatch`: use `appMatch.value` as is. Change it only when the site uses the words in a different sense; then list the unit in `appMatchDeviations` with the reason.
2. Names of screens, tabs, categories and features in the app are written exactly as the app's glossary and strings write them in this language. A parent looking for "Today's plan" in the app must find the same words.
3. `meta_title` and `meta_description` are the page's search result: write them the way a parent in that market searches for a baby activity app, not word for word. A `meta_description` is at most 160 characters (the build fails above that). No two titles or descriptions in the language may be identical, across pages.
4. FAQ (`faq.items.<id>.title`) is the question a parent types into a search engine; its `answer` starts with the direct answer, keeping en's answer-first order. Bullets keep en's count and order.
5. Numbers and facts stay exactly as en states them (340+ activities, 8 categories, ages 0–6, 13 years). In a guide that includes every study figure, year and age, and every country's screen-time guidance: a guide states which country says what, so never adapt it to your market. Write age spans and numbers in the language's usual form (0〜6歳, 0–6 Jahre).
6. `{{placeholders}}` stay exactly as in en. Every value is non-empty: the build rejects an empty string.
7. Keep untranslated: Babbby, Alu Studio, App Store, Apple ID, iCloud, iOS, iPhone, iPad, StoreKit, Firebase Analytics, Firebase Crashlytics, GRDB/SQLite, IDFA, CCPA, the email address. GDPR may use the regulation's official name in the language (DSGVO, RGPD) — once per page with GDPR in parentheses. A third-party service entry (`*.third_party.services.<n>.name` and `.url`) is copied exactly as en has it.
8. A guide `title` is the page title and a search result: write it the way a parent in that market types the question into a search engine, not word for word. `summary` is the index card and the meta description: at most 160 characters (the build fails above that). The first `content` paragraph answers the title directly — keep en's answer-first order. `content[i].items` keep en's count and order; an item that starts with an activity name followed by a colon keeps that shape, with the app's name for the activity (hard rules). Keep untranslated the names of studies, journals, institutions and official documents the guide cites (JAMA Pediatrics, Western University, Inserm, carnet de santé, BIÖG/BZgA, AEP); the translation may add the language's established name in parentheses once.
9. `landing.appstore_sub` and `landing.appstore_main` are the two lines of the App Store button (small, then large). Together they read as Apple's localized "Download on the App Store" badge in this language; `appstore_main` stays "App Store" unless that badge puts another word on the large line.
10. `footer.copyright` follows "© <year>" on the page. The effective dates (`*.effective_date`) use the language's own date format.
11. iOS paths in the privacy policy and FAQ (Settings → Privacy & Security → Analytics & Improvements) use the names iOS itself shows in this language.
12. Privacy policy and terms of use are translated in full like every other page — no note that the English version prevails. Keep their legal precision: every right, limit and disclaimer survives at full strength.
13. Punctuation follows the language as the shared l10n guidelines describe.

Write the packet's `output` path:

```json
{
  "lang": "<code>", "segment": "<packet.segment>",
  "units": [{"id": "...", "enHash": "...", "value": "<string for ui:, object shaped like en for guide:>"}],
  "appMatchDeviations": [{"id": "...", "reason": "<why the app's wording does not fit here>"}],
  "enIssues": [{"id": "...", "issue": "<what is wrong or ambiguous in the en source>"}]
}
```

- Every packet unit appears once in `units`. A `guide:` value has exactly the keys and nesting of its `en` (same number of `content` entries; an `{}` entry stays `{}`).
- `enIssues`: the en text is wrong, contradicts itself or the app, or cannot be translated without guessing. Still translate your best reading of en as written; the owner fixes en.

Then validate: `npm run -s l10n -- babbby apply <code> --dry-run <output path>`. Fix every rejected line and re-run until it reports `rejected 0`. Reply with one line: `<segment>: <n> translated, <d> appMatch deviations, <e> enIssues, dry run OK`.

## Task shape 3 — fix findings

The task gives a segment's packet path, your previous output and a list of reviewer findings with layer `translation`. Write a new file next to the previous output, `.logs/l10n/babbby/<code>/out/<segment>.fix<N>.json`, with the same header fields and only the units the findings name, following each finding unless it contradicts the app's glossary or strings, the site glossary or `appMatch` — then keep the established term and say so. Apply a finding's `suggested` value whole, or keep the current value whole and give the reason: never take half of a suggestion. Validate with the dry run and reply with `<segment>: <n> fixed, <k> kept (reason)`. Findings with layer `glossary` arrive as a separate task: edit the site glossary row, then re-translate every unit in the given packets that uses the term.
