# Sotto website translator contract

Read in full by the global `l10n-translator` agent (`~/.pi/agent/agents/l10n-translator.md`) before every Sotto site translation task — every Sotto packet names this file in its `contract` field, and the router `.pi/l10n/translator.md` sends the agent here; it overrides the shared l10n guidelines where they differ. Inputs: language code + glossary or packet path (+ findings for a fix).

You translate the website of Sotto — an iPhone and Android app for remembering the details about the people you care about: a private page per person with notes, sizes and measurements (ring size for every finger, shoe size), birthdays, gift ideas and conversation questions, all kept on the phone — from English into one target language. Readers are people in that market who found a page from a search: someone who keeps forgetting a friend's coffee order, needs a partner's ring size without asking, or wants a gift log, and decides whether Sotto fits. The guides are search landing pages; their questions are what readers type. The site must read like a warm, well-made product site written in that language, not like a translation.

The repo is the current working directory. The task names the language code (the sotto-ios lproj id, e.g. `ja`, `es`, `pt-BR`).

## Hard rules

- English is the only source. Never open, grep or quote the site's zh-Hant or zh-Hans files (`sotto/src/locales/zh-*`, `guides.zh-*.js`), the app's `zh-*.lproj`, or any other language's files, and never translate from Chinese. Ambiguity is resolved by the unit id, the page component that renders it (`grep -rn "<key>" sotto/src`), and the app's strings.
- The Sotto app already speaks this language, and it has no glossary file. Its wording reaches you as `appMatch` (the app's translation of an identical en string) and in the app's own strings, `~/Developer/alustudio/sotto/sotto-ios/Targets/Sotto/Resources/<code>.lproj/Localizable.strings` (en in `en.lproj`): a screen, button or field the site names (Gift Ideas, Left Ring, Pick a question) is written the way the app shows it. The site glossary (`packet.glossary.site`) fixes the words every page repeats. Both win over your own preferences. Read the site glossary before translating; `packet.glossary.app` is `null` for Sotto.
- Search terms per market: `~/Developer/alustudio/sotto/docs/marketing/aso-keywords.md` lists the terms people search for in each store locale (e.g. people notes, gift ideas, ring size). Prefer them where the sentence is about that thing; never stuff them in.
- You write exactly two kinds of file: the packet's `output` path (`.logs/l10n/sotto/<code>/out/<segment>.json`) and `sotto/l10n/glossary/<code>.md`. Nothing else — never the language's `translation.json` or `guides.<code>.js` (they are generated by `npm run l10n -- sotto apply`), never en, never code.
- Never run git commands that change state or anything that deletes files. The only commands you run are the dry run below and read-only searches.
- Other translators run in parallel in the same checkout. A helper script or scratch file goes under `.logs/l10n/sotto/<code>/scratch/<segment>/` only — never `/tmp` or a shared name.
- Your final message is the result: never call `contact_supervisor`.

## Task shape 1 — site glossary

The task says "Site glossary for <code>" and names the Sotto site. Open `sotto/l10n/glossary/<code>.md` (copied from `_template.md`). For every row fill "Term in language" with the one word or phrase every page will use, as a reader in that market searches for it; prefer the app's own wording (its `<code>.lproj/Localizable.strings`) for anything the app shows, and the market's search terms from `aso-keywords.md` for the product category. Leave "Note" for anything a translator must know (a term to avoid, a capitalization rule); write "from app strings" with the key when a row copies the app. Add a row for any other site-only word you expect to repeat (look over `sotto/src/locales/en/translation.json` and `sotto/src/data/guides/guides.en.js`). Keep the table format. Reply with the number of rows filled.

## Task shape 2 — translate a packet

The task gives a packet path (`.logs/l10n/sotto/<code>/packets/<segment>.json`). Each unit has:

| field | meaning |
|-------|---------|
| `id` | `ui:<dotted.key>` one UI string (a key ending `.0`, `.1` … is one item of a list); `guide:<slug>` one whole guide |
| `en` | the en text: a string for `ui:`; for `guide:` an object holding only the text fields (`title`, `summary`, `content[i].text`, `content[i].items`, and for a table `content[i].caption`, `content[i].head`, `content[i].rows`) |
| `enHash` | copy it unchanged into your output |
| `appMatch` | `ui:` only: the app has a string with exactly this en — `{key, value, note}` is the app's translation; `alternatives` lists other app keys translating it differently |
| `current`, `stale`, `previousEn` | an existing translation made from an older en (`previousEn`): revise `current` to the new meaning, keeping its wording where the meaning did not change |

Guide packets also carry `appTerms` (app screen and button names quoted in the guide); it is empty for Sotto, whose strings carry no role notes — check the app's strings yourself when a guide names something in the app. A content block with no text in `en` (`{}`) stays `{}`. The ring-size chart's rows are the app's conversion table and never appear in a packet: translate only its `caption` and `head`.

Per unit:

1. `appMatch`: use `appMatch.value` as is. Change it only when the site uses the words in a different sense; then list the unit in `appMatchDeviations` with the reason.
2. Names of screens, buttons and fields in the app are written exactly as the app shows them in this language. A reader looking for "Gift Ideas" in the app must find the same words.
3. A guide `title` is the page title and a search result: write it the way a reader in that market types the question into a search engine, not a word-for-word rendering. `summary` is the index card and the meta description: at most 160 characters (the build fails above that). The first `content` paragraph answers the title directly in two or three sentences — keep the en's answer-first order. No two titles or summaries in the language may be identical, across guides and UI strings (`meta_title`, `meta_description`).
4. `content[i].items` and a table's `head` and `rows` keep en's count and order (same rows, same cells per row). In a data table, numbers, years and citations stay as written (`McCormick, Salganik & Zheng, 2010`); translate the words around them.
5. `{{placeholders}}` stay exactly as in en. Every value is non-empty: the build rejects an empty string.
6. Keep untranslated: Sotto, iPhone, Android, Face ID, Touch ID, iCloud, Google Drive, Dropbox, App Store, Google Play, and the names of people, studies, books and products the guides cite (Threads; "1 in 8 Billion" keeps its title, and the translation may add the language's rendering after it in parentheses).
7. Register: warm and personal, the way the language's best consumer apps talk to one person. Keep the address form the site's pages in this language already use — German du, French vous, Spanish (Spain) tú, Italian tu, Portuguese (Brazil) você, Russian вы, Japanese です・ます, Korean 해요체, Arabic the second person singular — and keep it consistent across the segment. `es` is the Spain storefront: Spain usage, not Latin American.
8. Punctuation follows the language as the shared l10n guidelines describe. Arabic is shown right-to-left; keep Latin product names and numbers as they are.
9. Privacy policy and terms of use are translated in full like every other page — no note that the English version prevails.

Write the packet's `output` path:

```json
{
  "lang": "<code>", "segment": "<packet.segment>",
  "units": [{"id": "...", "enHash": "...", "value": "<string for ui:, object shaped like en for guide:>"}],
  "appMatchDeviations": [{"id": "...", "reason": "<why the app's wording does not fit here>"}],
  "enIssues": [{"id": "...", "issue": "<what is wrong or ambiguous in the en source>"}]
}
```

- Every packet unit appears once in `units`. A `guide:` value has exactly the keys and nesting of its `en` (same number of `content` entries; an `{}` entry stays `{}`).
- `enIssues`: the en text is wrong, contradicts itself or the app, or cannot be translated without guessing. Still translate your best reading; the owner fixes en.

Then validate: `npm run -s l10n -- sotto apply <code> --dry-run <output path>`. Fix every rejected line and re-run until it reports `rejected 0`. Reply with one line: `<segment>: <n> translated, <d> appMatch deviations, <e> enIssues, dry run OK`.

## Task shape 3 — fix findings

The task gives a segment's packet path, your previous output and a list of reviewer findings with layer `translation`. Rewrite only the units the findings name (keep the others byte for byte), following each finding unless it contradicts the app's strings, the site glossary or `appMatch` — then keep the established term and say so. Apply a finding's `suggested` value whole, or keep the current value whole and give the reason: never take half of a suggestion (a fix that drops part of what the reviewer asked for is flagged again next round). Validate with the dry run and reply with `<segment>: <n> fixed, <k> kept (reason)`. Findings with layer `glossary` arrive as a separate task: edit the site glossary row, then re-translate every unit in the given packets that uses the term.
